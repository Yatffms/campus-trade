# Redis 缓存：术语清单 & 待办（campus-trade）

> 用途：把“看得懂但记不住名字”的东西记下来；下次复习或面试前直接读这一页。

## 一、已经实现，要能自己讲清

| 名字（中/英） | 一句话 | 项目位置 |
|---|---|---|
| 旁路缓存 Cache-Aside | 读：先查缓存，没有再查库并回填；写：改库后删缓存 | `ItemCache.get/put/evict` |
| 缓存穿透 Penetration + 空值缓存 null caching | 查一个数据库里也没有的 id，缓存一个 `__NULL__` 挡住 | `ItemCache.putNull`，TTL 60s |
| 缓存雪崩 Avalanche + 随机 TTL（TTL jitter / 过期打散） | 大批 key 同时过期，给每个 key 的 TTL 加随机秒数，避免同时失效 | `ItemCache.put` 里 `10min + random(0..120s)` |
| 写时失效 | 改数据后删缓存，而不是改缓存 | `OrderServiceImpl.timeoutCancel` 里的 `evict` |

## 二、现在不做，记下来以后做

| 名字（中/英） | 一句话 | 备注 |
|---|---|---|
| 缓存击穿 Breakdown + 互斥重建 mutex rebuild | 热点 key 刚过期，N 个请求同时查库；只放一个去查，其余等 | 单机用 `ReentrantLock` + `tryLock(200ms)` + 二次检查 |
| 分布式锁 Distributed Lock | 多台机器时 `ReentrantLock` 不管用，要用 Redis `SET NX PX` 或 Redisson | 上云多实例后再做 |
| 逻辑过期 logical expiration | 击穿的另一种解法：缓存不设 TTL，值里带“逻辑过期时间”，过期后异步重建、先返回旧值 | 比互斥重建复杂，知道名字即可 |
| 计数器 + 定时回写 Write-Behind / 异步回写 | 浏览数先 `INCR` 到 Redis，定时任务按脏集合批量 `view_count = view_count + n` 落库 | 方案见下一节 |
| 脏集合 dirty set | Redis Set 记“哪些 id 被改过”，回写时按名单处理 | `item:view:dirty` |
| 回调 / 模板方法 Template Method（Java 用 `Supplier<T>` + lambda） | 把“查库”这个动作当参数传给缓存工具类，由工具类决定何时执行 | `getWithRebuild(id, () -> loadItem(id))` |
| 分段锁 Striped Lock | 用固定 64 把锁按 `id % 64` 分配，避免锁对象无限增长 | `rebuildLocks[Math.floorMod(id, 64)]` |
| 定时任务 @Scheduled(fixedDelay) | fixedDelay = 上次跑完后再等 N 毫秒；fixedRate = 固定频率 | 启动类已有 `@EnableScheduling` |

## 三、浏览量：简单版 vs 生产版

| | 简单版（现在做） | 生产版（以后做） |
|---|---|---|
| 计数 | `UPDATE item SET view_count = view_count + 1`（数据库原子自增） | Redis `INCR item:view:{id}` |
| 读取最新值 | 再 `SELECT view_count` 一次 | 缓存基线 + Redis 计数 |
| 落库 | 每来一次就落一次 | 定时任务批量落库 |
| 每次详情 SQL 数 | 2（UPDATE + SELECT） | 0（命中缓存时） |
| 缺点 | 热点商品行锁、库压力大 | 代码复杂：计数器、脏集合、回写任务、降级、并发击穿 |
| 适用 | 个人项目 / 低 QPS | 高 QPS、浏览量很大的场景 |

结论：QPS 低的时候“数据库原子自增 + 单独查一次”完全够用；把 Redis 那套记下来，作为“我知道更好的方案，但按当前量级选了简单的”的取舍说明。

## 五、面试怎么讲（一句话版）

- 缓存三兄弟：穿透→空值缓存/布隆过滤器；雪崩→TTL 打散；击穿→互斥重建或逻辑过期。
- 浏览量：低 QPS 用数据库原子自增；高 QPS 用 Redis 计数器 + 异步回写，读时“基线 + 增量”拼接。
