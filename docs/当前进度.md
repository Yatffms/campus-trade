## 第六轮的链路（面试就讲这个）

浏览器的「去支付」→ 后端校验（本人的单 / 没付过 / 没过期）→ 用**应用私钥**给参数签名，生成指向沙箱网关的表单 → 浏览器自动提交，跳到支付宝收银台 → 买家付款 → 支付宝 302 回跳 `return_url` → 后端**不信回跳参数**，拿 `out_trade_no` 调 `alipay.trade.query` 主动查单 → 只有 `TRADE_SUCCESS` 才改库 → `update ... where pay_status = 0` 保证幂等。

三条能讲出来的话：

1. 用的是「电脑网站支付」，签名表单由 SDK 生成，私钥只存在服务器本地文件里。
2. 回跳参数不可信，必须主动查单确认。
3. 落库用 `where pay_status = 0`，重复回跳/重复通知不会重复记账。

1. **未支付的订单也能被卖家确认成交** —— `OrderServiceImpl` 的 `confirm()` 缺 `pay_status == 1` 守卫（约 30 分钟）
2. **`notify_url` 异步通知没做** —— 用户付完直接关浏览器时回跳丢失；需要公网地址，上云后补（还要验签 + 幂等）

## 待办：支付倒计时（用户 2026-11-17 提出，暂缓）

下单后有 15 分钟支付期限，但页面上看不到“还剩多久”。计划在订单卡片上给「待支付」的单子加一个倒计时（拼多多那种 `剩 12:34`）。

实现要点（等收尾时一起做）：

1. **后端**：`VO/OrderVO.java` 目前没有 `expireTime` 字段，要补一个 `LocalDateTime expireTime`，并在 `OrderServiceImpl.toVO()` 里 `vo.setCreateTime(...)` 旁边补一行 `vo.setExpireTime(order.getExpireTime())`。不改这里，前端拿不到截止时间。
2. **前端**：只对 `status === 0 && Number(order.payStatus) === 0` 的卡片显示倒计时；用一个 `setInterval(1s)` 统一刷新所有倒计时，`visibilitychange` 隐藏时停掉，避免后台空转。
3. **到 0 的处理**：倒计时归零时**不要**在前端改状态——订单是后端 `OrderTimeoutTask`（每 60 秒扫一次）取消的，前端只提示“正在关闭订单…”并在 3 秒后重新拉一次列表。否则会出现“页面显示已超时、库里还是在售”的不一致。
4. **时区**：后端返回的是 `2026-11-17T18:30:00` 这种字符串，前端解析用 `new Date(s.replace('T', ' '))`，避免部分浏览器按 UTC 解析。

## 术语速查

- **穿透**：查库也没有 → 缓存空值挡（`__NULL__`，60 秒）
- **雪崩**：一批 key 同时过期 → TTL 加随机（10 分钟 + 0~120 秒）
- **击穿**：热点 key 刚过期、请求同时打库 → 互斥重建（TODO，没做）
- **幂等**：同一次支付处理多遍，结果一样（靠 `where pay_status = 0`）
- **主动查单**：拿商户订单号问支付宝“这单付了没”，`alipay.trade.query`
- **异步通知**：支付宝主动 POST 到你服务器（`notify_url`），比回跳可靠
