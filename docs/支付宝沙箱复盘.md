# 第 6 轮：支付宝沙箱支付 —— 全链路复盘

> 用途：过一段时间回头看这一轮，先读这一页，不要从代码开始读。

## 0. 一句话说清这一轮做了什么

用户点「去支付」→ 后端用**应用私钥**签一份"支付订单"表单 → 浏览器带着表单跳到**支付宝沙箱收银台** → 用沙箱买家账号付款 → 支付宝把浏览器**重定向回**我们的 return_url → 后端**不信**回跳参数，反过来调 `alipay.trade.query` **问支付宝"这单到底付了没"** → 确认 `TRADE_SUCCESS` 后，用一条**带 `where pay_status=0` 的 UPDATE** 把订单标记为已支付。

成功标志（2026-11-17 18:00 实测）：订单 #25、商品 #2「二手自行车」120.00，`pay_status=1`、`pay_time=2026-11-17 18:00:33`、`pay_no=2026111722001431020509715283`（支付宝真实交易号），商品 `status=2`（交易中）。

## 1. 参与这一轮的四个系统

| 系统 | 角色 | 它掌握什么 |
|---|---|---|
| 浏览器 | 载体：显示页面、提交表单、被 302 跳来跳去 | JWT（登录态）、页面 |
| 你的 Spring Boot | 下单方：生成表单、校验、查单、落库 | 应用私钥、支付宝公钥、数据库 |
| 支付宝网关（沙箱） | 验签、受理请求、返回结果 | 你的应用公钥（来自控制台）、自己的私钥 |
| 支付宝收银台页面 | 收钱的地方（买家用沙箱账号登录付款） | 买家账户、余额 |

沙箱里**没有"卖家"账户**：钱从买家账户进到**平台商户 PID**（`2088721102631010`），卖家分账只在你的 `orders` 表里记账。

## 2. 走的 8 步（含"这步排除了什么不确定性"）

| 步 | 做的事 | 关键产物 | 排除了什么疑问 |
|---|---|---|---|
| A1 | 开放平台开通沙箱，拿 APPID / 网关 / 密钥 / 两个测试账号 | 4 个参数 + 2 个账号 | 我们有没有资格调 |
| A2 | 把「应用私钥」「支付宝公钥」落到 `D:\alipay\*.txt` | 两个纯 Base64 文件 | 密钥格式对不对（BOM/头尾/换行） |
| A3 | 用命令行探针调 `alipay.trade.query` 查一个不存在的单号 | `40004 / ACQ.TRADE_NOT_EXIST` | **APPID+网关+私钥+公钥全对**（验签过了才会返回业务码） |
| B1 | `AlipayConfig` 读配置 + `AlipayClient` Bean；`/api/pay/ping` | `ping` 返回同样 40004 | SDK 接进来没问题 |
| B2 | `PayService.pagePayForm` 生成 `alipay.trade.page.pay` 表单，浏览器跳收银台 | 一段自动 submit 的 HTML | 生成表单/跳转/签名对不对 |
| B3 | `/api/pay/return` 接回跳，打印查单结果（先不写库） | 一张表格：code/trade_status/total_amount | 回跳参数能不能拿到、查单能不能查到 |
| B4 | `orders` 加三列 + `OrderVO` 补三字段 + 幂等 UPDATE 落库 | `pay_status=1` 的订单 | 支付结果能不能安全落库 |
| B5 | 15 分钟超时 + 已支付守卫（timeoutCancel / cancel） | 未付款自动取消、已付款不被误取消 | 超时和支付会不会互相踩 |

**A3 是整轮里性价比最高的一步**：它把"我的代码写错了"和"我的密钥配错了"提前分开了。没有 A3，B1/B2 报错时你根本不知道往哪查。

## 3. 四次跨系统传递，各传了什么

### 传递 1：浏览器 → 你的后端（拿支付表单）
```
GET /api/pay/page?orderId=25
Authorization: Bearer <JWT>
                ↓
后端：查订单 → 校验（是我的单？没付款？没过期？）→ 拼 biz_content → 用应用私钥签名 → 返回 HTML
```
返回的 HTML 长这样（就一个 input，其余参数都在 action 的 query 上）：
```html
<form id="alipaysubmit" name="alipaysubmit" action="https://openapi-sandbox.dl.alipaydev.com/gateway.do?app_id=...&method=alipay.trade.page.pay&sign=...&sign_type=RSA2&..." method="POST">
  <input type="hidden" name="biz_content" value='{"out_trade_no":"CT25","total_amount":"120.00","subject":"...","product_code":"FAST_INSTANT_TRADE_PAY"}'>
</form>
<script>document.forms['alipaysubmit'].submit();</script>
```

- `out_trade_no` = **你**给这单的编号（本项目 `"CT" + orderId`）
- `total_amount` = 金额，**必须是字符串**（`"120.00"`，不是 `120`）
- `product_code` = `FAST_INSTANT_TRADE_PAY`（电脑网站支付固定值）
- `sign` = 应用私钥对"待签串"的签名

### 传递 2：浏览器 → 支付宝（跳收银台）
浏览器自动 submit 表单 → 支付宝网关用**你在控制台上传的应用公钥**验签 → 验过就给收银台页面 → 买家登录付款 → 支付宝生成 `trade_no`（支付宝的流水号）。

**这一步的验签方是支付宝，签名的私钥在你服务器上。** 所以私钥一旦泄露，别人就能替你的商户号发起支付请求。

### 传递 3：支付宝 → 浏览器 → 你的 return_url（同步回跳）
付款成功后，支付宝把浏览器 302 到：
```
http://localhost:8080/api/pay/return?out_trade_no=CT25&trade_no=2026...&total_amount=120.00&sign=...
```
⚠️ **这些参数在浏览器地址栏里，用户可以随便改。** 所以后端的原则是：**回跳参数只用来"知道是哪一单"，不要用来判断"付没付"。**

### 传递 4：你的后端 → 支付宝（主动查单，这才是真相）
```
后端：alipay.trade.query { "out_trade_no": "CT25" }
                ↓ 用应用私钥签名
支付宝：用你的应用公钥验签 → 查库 → 返回
       {"code":"10000","trade_status":"TRADE_SUCCESS","total_amount":"120.00","trade_no":"..."}
                ↓ 支付宝用自己的私钥给响应签名
SDK：用本地「支付宝公钥」验响应的签名 → 通过才给你 Response 对象
```
这一步是**闭环的证据**：只有 `code=10000` 且 `trade_status ∈ {TRADE_SUCCESS, TRADE_FINISHED}` 才算付款成功。

### 之后：落库（幂等）
```sql
UPDATE orders
   SET pay_status = 1, pay_time = NOW(), pay_no = ?
 WHERE id = ? AND pay_status = 0
```
`rows == 1` = 这次是第一次落库；`rows == 0` = 之前已经落过了（重复回跳、刷新、并发），什么都不做。**幂等不是靠 if 判断，是靠 WHERE 条件。**

## 5. SDK 为什么看着复杂（4 个概念）

1. **`AlipayClient` 本质是"会自动签名的 HTTP 客户端"。** 你写 `client.execute(request)`，它背后做：拼公共参数 → 生成待签串 → 用应用私钥 RSA2 签名 → POST 到网关 → 拿响应 → 用支付宝公钥验签 → 反序列化成 `Response` 对象。**所以你的代码里一个"签名"字样都没有，全在 SDK 里。**
2. **每个接口一个 Request/Response 类**：`AlipayTradePagePayRequest`、`AlipayTradeQueryRequest`… `biz_content` 是一段 **JSON 字符串**，SDK 不帮你生成，所以要手写那一堆 `\"` 转义。
3. **`pageExecute` ≠ `execute`**：`pageExecute` **不发请求**，只生成一段 HTML 表单（给浏览器跳转用）；`execute` 才真的发 HTTP（查单用）。这是最容易混的一点。
4. **判定要两段看**：先 `code`（`10000` 成功 / `40004` 业务失败 / `20000` 未知），再看 `trade_status`。

## 6. 如果重新来过，按这个顺序写（重要）

**核心原则：每一步都要有"能独立看到的成功信号"，错一步只回退一步。**

1. **能证明配置对的最小东西**：`/api/pay/ping` 查一个不存在的单号 → 看到 `ACQ.TRADE_NOT_EXIST` 就停手，先别写业务。（没有这步，后面所有报错都分不清是签名还是业务）
2. **能生成表单**：`pagePayForm` 先用写死的金额 0.01 → 浏览器打开 `/api/pay/page` → 看到收银台就算过。
3. **能回来**：`/api/pay/return` 只**打印**查单结果，不写库 → 确认能拿到 `trade_status`。
4. **再动数据库**：`orders` 加三列 → `Order`/`OrderVO` 补字段 → 写幂等 UPDATE。（表结构放后面，因为前 3 步用固定金额就能测）
5. **最后写守卫**：15 分钟超时、`timeoutCancel`/`cancel`/`confirm` 的 `pay_status` 判断。
6. **前端和放行配置**在联调前补：`WebMvcConfig` 放行 `/api/pay/return`（回跳没有 token）、`goPay` 用同页跳转（新窗口会被拦）。

## 7. 三个最容易混的点

1. **沙箱没有"卖家"**：钱进平台商户 PID，卖家只是 `orders` 表里的 `seller_id`。
2. **`return_url` 不是控制台里的"回调地址"**：它是代码里 `request.setReturnUrl(...)` 传的；控制台里那个"应用网关/授权回调"跟它无关。
3. **`out_trade_no` vs `trade_no`**：前者是**你**的订单号（`CT25`），后者是**支付宝**的交易号（20 位数字）。对账、退款都用 `trade_no`。
